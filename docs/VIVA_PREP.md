## Question 1: Why did you choose AES-256-GCM over AES-CBC or AES-ECB?
**Answer:**
- **AES-ECB** (Electronic Codebook) is completely insecure for healthcare data because identical 16-byte plaintext blocks produce identical ciphertext blocks (the infamous "ECB Penguin" leakage).
- **AES-CBC** (Cipher Block Chaining) provides confidentiality, but **does not provide message integrity or authenticity**. To achieve integrity with CBC, one must implement an "Encrypt-then-MAC" scheme using HMAC-SHA256, which is error-prone and vulnerable to padding oracle attacks (e.g., POODLE).
- **AES-GCM** (Galois/Counter Mode) is an **Authenticated Encryption with Associated Data (AEAD)** standard. It provides both confidentiality (using Counter mode) and cryptographic integrity/authenticity (using a Galois field multiplier GMAC) in a single algorithm. It produces a 16-byte authentication tag that guarantees the data has not been modified.

## Question 2: How does AES-256-GCM detect tampering? What happens mathematically?
**Answer:**
During encryption, the Galois Hash (GHASH) function calculates an authentication tag $T$ over the ciphertext and optional associated data using a hash subkey $H = \text{AES}_K(0^{128})$ in the finite field $\text{GF}(2^{128})$:
$$T = \text{GHASH}_H(A, C) \oplus \text{AES}_K(J_0)$$
During decryption, `cipher.decrypt_and_verify(ciphertext, auth_tag)` recalculates the tag. If an attacker tampers with even a single bit of the ciphertext or tag in SQLite, the polynomial evaluation over $\text{GF}(2^{128})$ yields a completely different tag. The verification check hard-fails with a `ValueError` in PyCryptodome. The application catches this, immediately raises an `IntegrityTamperedError`, refuses to display any data, and appends a `TAMPER_DETECTED` alert to the audit log.

## Question 3: Why must a fresh random 12-byte nonce (IV) be generated for every encryption?
**Answer:**
In GCM mode, the keystream is generated by encrypting successive counter values starting from the initial counter derived from the nonce: $IV \parallel 0^{31}1$.
If the same key and nonce pair is **ever reused** to encrypt two different messages $P_1$ and $P_2$:
1. The XOR of the ciphertexts reveals the XOR of the plaintexts: $C_1 \oplus C_2 = P_1 \oplus P_2$.
2. Worse, an attacker can solve for the hash key $H$ in $\text{GF}(2^{128})$, completely breaking the authentication mechanism and allowing the attacker to forge valid tags for arbitrary ciphertexts.
Therefore, our `CryptoService.encrypt_record()` strictly generates a fresh, cryptographically secure 12-byte nonce using `Crypto.Random.get_random_bytes(12)` on every write and update operation.

## Question 4: Why use scrypt for password hashing instead of SHA-256, MD5, or static salts?
**Answer:**
- **MD5 and SHA-256** are fast cryptographic hash functions designed for message digest throughput, not password storage. Modern GPUs and ASICs can compute billions of SHA-256 hashes per second, making offline dictionary attacks trivial.
- **scrypt** is a **memory-hard key derivation function** (RFC 7914). It requires both substantial CPU computation and a large, configurable amount of RAM to compute each hash. Because hardware attackers (GPUs/FPGAs) have limited fast memory per core, scrypt drastically increases the hardware cost and time needed to perform brute-force password cracking by multiple orders of magnitude.
- Werkzeug automatically generates a fresh, cryptographically secure random salt for every user, preventing rainbow table attacks.

## Question 5: Why is Role-Based Access Control (RBAC) enforced server-side instead of just in the frontend?
**Answer:**
In web applications, the client is untrusted. Hiding an "Edit" button in HTML/CSS only prevents honest users from clicking it. A malicious user or curious nurse can:
1. Inspect the DOM and unhide the button.
2. Directly navigate to `/patients/1/edit` in the browser URL bar.
3. Send raw HTTP `GET` or `POST` requests via cURL, Postman, or Python scripts.
Our architecture enforces authorization at the HTTP route layer using the `@require_permission` decorator before any route handler executes. If a Nurse hits `/patients/1/edit`, the server immediately halts processing, returns an HTTP `403 Forbidden` response, and permanently logs an `ACCESS_DENIED` security violation.

## Question 6: How does the SHA-256 hash-chaining work in your audit trail?
**Answer:**
Each audit row stores:
- `prev_hash`: The SHA-256 digest of the immediately preceding record (or 64 zeros for the genesis block).
- `record_hash`: $\text{SHA-256}(\text{prev\_hash} \parallel \text{user\_id} \parallel \text{username} \parallel \text{action} \parallel \text{resource} \parallel \text{status} \parallel \text{details} \parallel \text{timestamp})$.
If an insider or attacker modifies any row in the SQLite database (e.g., changing an `ACCESS_DENIED` action to `LOGIN_SUCCESS`), that row's recalculated hash will no longer match its stored `record_hash`, and all subsequent rows' `prev_hash` links will break. Our `AuditService.verify_chain()` scans the chain from block 1 to $N$ and pinpoint-detects the exact modified row.

## Question 7: How did you demonstrate the difference between HTTP and HTTPS using Wireshark?
**Answer:**
- Under unencrypted **HTTP (port 5000)**, capturing packets with Wireshark reveals the raw TCP stream containing plaintext HTTP `POST /login` requests. The parameters `username=doctor_alice` and `password=DocSecurePass#2026`, as well as the plaintext `session` cookie, are visible in clear text to anyone on the network.
- Under **HTTPS (TLS 1.3 / TLS 1.2)**, Wireshark captures show the TLS Handshake (Client Hello, Server Hello, Key Exchange, and Certificate presentation). All subsequent data packets are encapsulated in encrypted `Application Data` protocol records. Neither the URL path, the credentials, the session cookie, nor the patient clinical data can be read by an eavesdropper.

## Question 8: How does the application defend against Cross-Site Request Forgery (CSRF)?
**Answer:**
We implement the **Synchronizer Token Pattern** using `Flask-WTF` (`CSRFProtect`). When an authenticated user renders any form, Flask generates a unique, cryptographically random, session-bound token stored in the session cookie and injected as a hidden field `<input type="hidden" name="csrf_token" value="...">`. When a POST request is submitted, the server validates that the submitted token matches the session token. Because a malicious cross-origin site cannot read the token due to the browser's Same-Origin Policy (SOP), forged cross-site requests are rejected with `400 Bad Request`.

## Question 9: What is Session Fixation and how is it mitigated?
**Answer:**
In a session fixation attack, an adversary tricks a victim into authenticating using a pre-existing session ID known to the attacker. If the server does not rotate the session ID upon authentication, the attacker can hijack the victim's authenticated session.
In `AuthService.authenticate_user()`, the very first operation upon validating credentials is `session.clear()`. This destroys any pre-existing session identifiers and issues a completely fresh, cryptographically random session cookie to the user.

## Question 10: How do security headers protect the application?
**Answer:**
Via **Flask-Talisman**, the application automatically sets:
- `Content-Security-Policy (CSP)`: Restricts script, style, and font origins to `'self'`, blocking Cross-Site Scripting (XSS).
- `X-Frame-Options: DENY`: Prevents the healthcare portal from being embedded in an `<iframe>`, preventing Clickjacking attacks.
- `X-Content-Type-Options: nosniff`: Prevents MIME-sniffing vulnerabilities in browsers.
- `Strict-Transport-Security (HSTS)`: Instructs browsers to communicate exclusively over HTTPS.
- `SameSite=Lax` and `HTTPOnly=True` on cookies: Ensures JavaScript cannot read session cookies (`document.cookie`), neutralizing cookie-theft XSS payloads.

## Question 11: What is Additional Authenticated Data (AAD) in AES-256-GCM, and how does ArogyaRaksha use RFC 8785 Canonical JSON to prevent ciphertext transplantation?
**Answer:**
Standard encryption encrypts plaintext into ciphertext without mathematically binding it to the database row or tenant where it belongs. An attacker with database write access could copy Patient A's encrypted diagnosis ciphertext into Patient B's database row (ciphertext splicing / transplantation).
To eliminate this, AES-256-GCM supports **Additional Authenticated Data (AAD)**: data that is not encrypted, but is fed into the Galois field GMAC tag calculation. ArogyaRaksha serializes AAD using **RFC 8785 Canonical JSON**:
```json
{"patient_id": "P-001", "tenant_id": "tenant-alpha", "version_id": 1}
```
During decryption, if the ciphertext is evaluated against a different patient ID or different tenant ID, the GMAC verification fails immediately with a `ValueError("MAC check failed")`. The service catches this, raises `IntegrityTamperedError`, halts rendering, and logs a `TAMPER_DETECTED` alert.

## Question 12: How does your Multi-Tenant Architecture enforce organization isolation, and what is the Emergency Break-Glass protocol?
**Answer:**
- **Tenant Isolation:** Every primary model (`User`, `Patient`, `AuditLog`) binds an indexed `tenant_id` foreign key. The `PolicyEngine` evaluates every request against the authenticated user's tenant. Any attempt by a clinician in Hospital Beta to view or modify records in Hospital Alpha returns HTTP `403 Forbidden` and logs a `CROSS_TENANT_ATTEMPT` audit event.
- **Segregation of Duties:** System Administrators are strictly prohibited from mutating clinical records (`CREATE`, `UPDATE`, `DELETE`), enforcing statutory clinical privacy.
- **Emergency Break-Glass:** In acute emergency situations, an attending physician who is not the assigned primary doctor can override the assignment gate by declaring an emergency justification string (`break_glass_reason`). The request is permitted while instantly logging an immutable `BREAK_GLASS_ACCESS` audit entry and firing real-time webhook alerts to the Clinical Director and SOC.

## Question 13: What is Optimistic Concurrency Control (OCC) and how does it prevent the "Lost Update" problem?
**Answer:**
In busy hospitals, two clinicians (e.g. Doctor and Triage Nurse) may open the same patient chart simultaneously. Under naive database writes, whichever clinician saves last silently overwrites the other clinician's notes ("Lost Update" anomaly).
ArogyaRaksha uses an integer `version_id` column on the `patients` table:
1. When rendering the edit form, the current `version_id` (e.g. 1) is passed to the client.
2. Upon submission, the update query executes:
   $$\text{UPDATE patients SET ..., version\_id = version\_id + 1 WHERE id = :id AND version\_id = :expected\_version}$$
3. If another clinician committed an update first, `version_id` is now 2. The query affects 0 rows.
4. `PatientService` detects this, aborts the commit, raises `ConcurrencyConflictError`, and returns HTTP `409 Conflict`, prompting the user to reload the fresh chart without losing either update.
In our 10-thread benchmark, racing on version 1 resulted in exactly 1 atomic commit and 9 caught 409 conflicts with zero lost edits.

## Question 14: Why did you implement a Server-Side Session Store, and how does instant session revocation work?
**Answer:**
- Standard Flask stores serialized session payloads in client-side signed cookies. While tamper-resistant, client-side cookies cannot be revoked by the server until they expire; an attacker possessing a stolen cookie can remain logged in even if the administrator disables the account or the user changes their password.
- ArogyaRaksha implements `ServerSideSessionInterface` backed by Redis or Memory:
  1. The browser cookie contains only a 256-bit cryptographically random opaque token (`_sid`).
  2. All authenticated session state (`user_id`, `role`, `tenant_id`) is stored exclusively server-side.
  3. Enforces 15-minute idle timeouts and 8-hour absolute lifespans.
  4. Each user has a `session_version` integer in the database. When a user logs out, resets their password, or has their account locked by an administrator, `session_version` increments, instantly invalidating all active sessions across all devices in real time.

## Question 15: What is the Transactional Outbox pattern, and why is it needed for security alerting?
**Answer:**
When a critical security event occurs (e.g. `TAMPER_DETECTED` or `BREAK_GLASS_ACCESS`), sending HTTP webhook alerts directly inside the web request loop creates the "Dual-Write Problem": if the external webhook endpoint is slow or times out, the clinical database transaction hangs or fails; conversely, if the database commits but the network drops before the webhook sends, the security alert is permanently lost.
ArogyaRaksha uses the **Transactional Outbox Pattern**:
1. When an event occurs, an `OutboxEvent` row is inserted into the database in the exact same atomic transaction as the clinical mutation.
2. A resilient background dispatcher polls `PENDING` events using PostgreSQL `SELECT ... FOR UPDATE SKIP LOCKED` row locking.
3. Events are delivered with exponential backoff retries, HMAC-SHA256 signatures, replay-defense nonces, and a circuit breaker, guaranteeing at-least-once delivery without degrading clinical request latency.
